# 性能评估与可升级方向

## 已完成的真实 CPU 测量

日期：2026-10-16。机器：Intel Core Ultra 9 285H，16 核/16 逻辑处理器，约 64 GiB 内存，Intel Arc。本轮没有 NVIDIA GPU。

模型：官方 inaSpeechSegmenter 0.8.0 `smn`；TensorFlow 2.21.0；Python 3.12.15；Docker/WSL2 Linux x86_64，项目位于 Windows 挂载目录。计算库线程配置为 2；该基准容器没有施加生产 Compose 的 2 CPU 硬配额。

样本：上游公开 `musanmix.wav`，时长 **74.5229375 秒**，固定提交 `7a41b809c3cc6d8d36b24e70784779f8d16f7b5e`，SHA-256 `f325193b727fefae46a8865747aacd50faa9a33e76924bcb9ebb5eb2d4c339ee`。它是 MUSAN 开放许可音频的混合测试材料，来源说明保留在本地验收目录；没有将媒体再分发进本项目制品。

每项串行测量 3 次，取中位数。各项都重新执行官方特征提取、CNN 和 Viterbi；只在“缓存命中”项跳过推理。所有计时样本的合并分类区间均与参考一致。性别基线只在对比时合并 male/female 为 speech。

| 场景 | 中位耗时 | RTF：耗时/音频时长 |
| --- | ---: | ---: |
| 同一 Python 进程内，每次重载模型，batch 32，关闭性别识别 | 2.3782 秒 | 0.03191 |
| 常驻模型，batch 32，关闭性别识别 | 1.7490 秒 | 0.02347 |
| **常驻模型，batch 128，关闭性别识别** | **1.3224 秒** | **0.01774** |
| 常驻模型，batch 128，开启性别识别 | 2.4587 秒 | 0.03299 |
| 相同 WAV 的内存结果缓存命中 | 0.000703 秒 | 不代表新音频推理 |

最终配置相对本表重载基线耗时降低约 **44.4%**，处理吞吐约为其 **1.80 倍**。batch 128 相对常驻 batch 32 的耗时降低约 **24.4%**；关闭性别识别相对同 batch 的性别基线降低约 **46.2%**。这些百分比涉及不同基线，不能相加。

首次 TensorFlow 导入加模型加载在该次进程中约 **52.79 秒**，未计入每片段的稳态表格。首轮观测约 40.58 秒，说明启动耗时受文件缓存和跨系统挂载影响。常驻服务避免每个请求重复导入，不能保证所有机器的首次启动都一样快。

以上计时从规范 WAV 开始，不含宿主 FFmpeg、网络传输、排队和宿主其余分析。Windows → 实际 Compose 服务 → 宿主 DTO 的完整链路已独立验证功能，但没有把它冒充为相同口径的吞吐基准。

原始样本、全部耗时及 profile 记录见 [benchmark-cpu.json](evidence/benchmark-cpu.json)。单一样本不能证明中文直播准确率、不漏检唱歌或任意硬件提速，RTF 小于 1 也不能保证多路直播无排队。

## 本版已经采用的优化

| 优化 | 收益依据 | 边界 |
| --- | --- | --- |
| 独立服务常驻模型 | 避免反复 TensorFlow 导入与模型加载 | 占用常驻内存，需要明确启动和停止 |
| 关闭性别识别 | 本任务只需要音频类别，真实对比减少推理耗时 | 不提供性别标签 |
| 默认 batch 128 | 本机比 batch 32 更快且区间一致 | GPU/低内存机器须自行复测，可调整 |
| 有界内容缓存 | 重试相同 WAV 时无需再次推理 | 新片段不享受此收益；仍须上传并计算内容哈希 |
| 限制计算线程及单模型并发 | 控制对宿主 ASR 的资源竞争 | 不是吞吐必然更高的承诺 |
| 规范 PCM、服务端跳过再次 FFmpeg | 传输格式固定，服务不重复解码 | 现有宿主接口没有原始 PCM，宿主仍额外解码一次 |

不会通过抽样跳过大段音频、降低采样率、减少候选或改变分类阈值来制造速度提升。

## 下一步值得评估，但本版没有宣称实现的升级

1. **ONNX 推理后端**：转换固定 CNN、验证预处理和输出后再比较 CPU/CUDA。可能降低 TensorFlow 启动及依赖体积，但需要检查算子支持、动态 batch、Viterbi 前的概率及 20 ms 边界。官方安装包中的 ONNX Runtime 主要还服务其他模型，不能据此认为本版 CNN 已经走 ONNX。
2. **宿主转写前音频分析接口**：只有新增正式接口、共享已经解码的 PCM，才可能消除一次解码或用于 ASR 调度。需要新的宿主修改及误分类回归，本次没有改主程序，也没有预先过滤音乐。
3. **Viterbi / 区间归并的 C、Cython 或 Rust 内核**：这些循环可研究降低常数开销；但状态数固定为 2/3，基础计算已经接近按帧线性。更换语言不自动降低时间复杂度。当前 profile 的主要耗时链在 TensorFlow，需先独立量化这些循环的占比，再决定是否值得增加编译和多平台维护。
4. **更大 batch、GPU、混合精度**：必须有目标硬件测量，并检查每个样本的类别、区间边界及内存峰值；不能把“可以使用 CUDA”写成“必然更快”。

FFT、矩阵运算和 CNN 本来已经大量使用编译实现。单纯把 Python 调用包装改写成 C/Cython，不代表能让这些底层运算再次加速。模型转换和量化也可能改变分类结果，不能只看速度验收。

## 复现

先准备真实官方模型，性别模型仅用于基线：

```text
python -m blc_inaspeech prepare-models --model-dir .local/models --include-gender
python scripts/benchmark.py --model-dir .local/models --wav /path/to/musanmix.wav --output .local/benchmark-cpu.json --iterations 3
```

基准在独立 Linux 运行环境执行。样本来源为 [固定上游文件](https://github.com/ina-foss/inaSpeechSegmenter/blob/7a41b809c3cc6d8d36b24e70784779f8d16f7b5e/media/musanmix.wav)。下载后先核对上述 SHA-256。

生产服务与基准不要同时抢占机器资源。不同线程设置、CPU 配额、文件系统和 TensorFlow 构建不能直接作百分比比较。缓存结果和首次加载必须分别报告。
